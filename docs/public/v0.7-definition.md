# v0.7 Definition

Agent Data Hub v0.7 should make a small public release candidate evidence-led.

The goal is not to become a packaged product, hosted service, or broad
automation platform. The goal is to make sure a public tag is cut only from a
commit whose local and CI evidence proves the important loops separately.

## v0.7 Release Candidate Loop

The v0.7 loop is:

1. Start from a fresh checkout and install it with `pip install -e .`.
2. Run the isolated public demo database and public demo smoke.
3. Register a temporary local project through `agent-hub register-project`.
4. Prove the multi-agent trust loop from draft to reviewed memory.
5. Prove offline agent behavior writes no reviewed memory.
6. Prove the baseline-to-head upgrade drill.
7. Confirm `agent-hub status` and `agent-hub check` are green.
8. Update release notes and follow the release checklist before tagging.

## What Must Be Proven

v0.7 requires these checks as separate evidence, locally where practical and in
CI for every pushed release candidate:

```bash
scripts/release_candidate_check.sh
.venv/bin/python -m pytest -q
scripts/db_start_public_demo.sh
scripts/smoke_public_demo.sh
scripts/smoke_external_developer.sh
scripts/smoke_trust_loop.sh
scripts/smoke_agent_offline.sh
scripts/upgrade_drill.sh
agent-hub status
agent-hub check
```

`scripts/release_candidate_check.sh` is a local convenience runner for the same
evidence set. It does not tag, publish, recover, or change release metadata.

CI must keep the major behavioral smokes as separate jobs. A green unit-test
job is not enough evidence for release readiness.

## What Stays Out

v0.7 still does not mean:

- PyPI or Homebrew distribution
- hosted deployment
- production authentication or roles
- background sync workers
- automatic recovery or restart
- automatic memory capture
- write-capable MCP tools
- treating OKF export as a second source of truth

## Acceptance Bar

ADH reaches this v0.7 bar when the public docs and release checklist make the
release-candidate evidence explicit, CI proves the separate behavior loops on
`main`, and a maintainer can decide whether to tag without reconstructing the
project's operational state from memory.
