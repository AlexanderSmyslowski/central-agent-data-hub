# v1.0 Definition

Agent Data Hub v1.0 should be boringly reliable reviewed context infrastructure
for local agent work.

That means a developer can use it as a small local system for verified context,
not as a memory grabber, hosted product, or automation platform. The core claim
is still narrow:

```text
verified context for humans and agents
```

## v1.0 Operating Loop

The v1.0 loop is:

1. Install from a fresh checkout.
2. Start the neutral public demo.
3. Register one real local project.
4. Start an agent run from reviewed project context.
5. Let unreviewed inputs become drafts, not facts.
6. Review drafts explicitly through CLI, Hub View, or an approved adapter.
7. Prepare a task-specific context pack with trail, gaps, and review labels.
8. Finish the run with a handoff.
9. When reviewed memory was written, export, verify receipts, and create a
   verified backup.
10. If the Hub is offline, stop clearly before claiming writeback, export, or
    backup completion.

## What Must Be Proven

v1.0 requires evidence for these paths:

```bash
scripts/v1_readiness_check.sh
scripts/release_candidate_check.sh
scripts/restore_drill.sh
scripts/agent_start.sh --project <project-slug> --query "<focus>" --review
scripts/agent_finish.sh --project <project-slug> --review --export --backup
scripts/memory_receipt.sh --project <project-slug> --since 24h
agent-hub prepare --project <project-slug> --task "<task>" --format json
agent-hub doctor
agent-hub status
agent-hub check
```

The readiness check must verify that this contract is wired to concrete local
evidence, then run the release check. The release check must include separate
behavioral proofs for the public demo, first external project, trust loop,
offline-agent behavior, upgrade drill, restore drill, and runtime health.
Backup completion must mean a dump was written and the latest timestamped local
backup was restored and checked.

## Required Properties

- Project boundaries are explicit before context is loaded.
- Reviewed memory is distinguishable from drafts in every agent-facing output.
- Draft promotion is always an explicit human review action.
- Read-only surfaces cannot write, except for the two audited Hub View review
  actions: accept one draft or reject one draft.
- MCP remains read-only.
- Backup, restore, status, check, and doctor paths are understandable without
  private operator knowledge.
- Stale and orphaned run locks are visible, and orphaned lock cleanup is an
  explicit local operator action.
- Public demo data is neutral and physically separated from operator data.
- Failure messages name the likely local problem and the next safe command.

## What Stays Out

v1.0 still does not mean:

- hosted SaaS
- multi-user authentication or permissions
- background daemons or automatic restart loops
- write-capable MCP tools
- automatic promotion, demotion, or review
- embeddings or semantic indexing as a requirement
- OKF import or two-way sync
- storing raw chats, secrets, private customer data, or sensitive exports

## Acceptance Bar

ADH reaches this v1.0 bar when a new local user and the maintainer can both run
the documented loop, the evidence scripts stay green, and common host failures
produce clear offline or diagnostic behavior instead of partial success claims.

The result should feel like dependable local infrastructure: small, explicit,
reviewed, recoverable, and honest about what it does not do.
